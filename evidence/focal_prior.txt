0. HEADLINE
================================================================
All four questions resolve, and three of them against the task's priors.

1. DEFAULT / FALLBACK = 35.0 exactly, stored as a **float64** double
   (bits 0x4041800000000000) in four independent places, including the
   estimation-failure path. [PROOF]
2. The plausible-range clamp is **[10.0, 1000.0]** — NOT a 35-centric
   window. It is `max(10, min(f, 1000))` at 0x7a17ea-0x7a1806. [PROOF]
   Critically it clamps the **metadata/prior** focal, and is *not* applied
   to the geometric estimate. [PROOF]
3. There is **no weighted prior term** in the estimator at all. Prior and
   geometric estimate are mutually exclusive (winner-take-all on the
   FocalMode switch), so "the prior weight" is not a number — it is
   effectively infinite when metadata exists. [PROOF + INFERENCE]
4. The pixel->mm conversion uses a **fixed full-frame 36 x 24 mm sensor**,
   via its diagonal hypot(36,24) = 43.266615 mm. 36.0 confirmed; the short
   edge 24.0 is the constant actually in the divide. [PROOF]

1. THE 35.0 DEFAULT (question 1)
================================================================
The value 35.0 is a double, bit pattern 0x4041800000000000, emitted as
`48 b8 00 00 00 00 00 80 41 40` (movabs $0x4041800000000000,%rax).
The 8-byte LE image of 35.0 also sits as data at slice 0x321abb0.

  slice 0x321abb0  FAT 52,554,672  raw 0000000000804140  = 35.0   [PROOF]
        constant in a hand-written double block (see 5.2)

Four movabs sites, all writing the focal field:

  slice 0xb62da0  FAT 11,955,616   ctor: `movq %rax,0x28(%rdi)` at 0xb62daa
                                   -> focal field default at object +0x28.

                                   defaults, from 0x3219cc0) and +0x20 = 0

  slice 0xb63c01  FAT 11,959,297   solver param block init: 35.0 -> the
                                   param slot that is later overwritten with

  slice 0xb65c4d  FAT 11,967,565   settings DESERIALISER: 35.0 is written to
                                   the focal temp at -0x198 BEFORE
                                   "UprightFocalLength35mm" is read into the
                                   same slot at 0xb65c95. Missing key =>
                                   stays 35.0. [PROOF]
  slice 0xb64279  FAT 11,960,953   THE ESTIMATION-FAILURE FALLBACK. [PROOF]

Plus two direct assignments from the 35.0 constant (not movabs):
  slice 0x7a16f1  FAT 8,017,649   `movsd 0x321abb0,%xmm0` then

Reading: 35 is a triple-duty literal — constructor default, deserialiser
default, and hard failure value. It is also the top of the plausible *prior*
range in the Adobe UI sense (a 35 mm full-frame normal lens), which is why
it is a safe fallback rather than a measured value.

================================================================
2. THE PLAUSIBILITY CLAMP [10, 1000] (question 2)
================================================================
One clamp, two instructions, both in the focal-preparation function at
0x7a15c0.. (this function supplies the prior/metadata focal for the K
matrix):

  slice 0x7a17ea  FAT 8,017,898  movsd -0xe40(%rbp),%xmm1   ; xmm1 = focal
  slice 0x7a17f2  FAT 8,017,906  minsd 0x321ac70(%rip),%xmm1 ; min(f,1000)
  slice 0x7a17fa  FAT 8,017,914  movsd 0x2da2e18(%rip),%xmm0 ; xmm0 = 10.0
  slice 0x7a1802  FAT 8,017,922  maxsd %xmm1,%xmm0           ; max(10,prev)
  slice 0x7a1806  FAT 8,017,926  movsd %xmm0,-0xe70(%rbp)    ; clamped focal

  bounds:
    slice 0x2da2e18  FAT 47,869,464  raw 0000000000002440  = 10.0    [PROOF]
    slice 0x321ac70  FAT 52,554,864  raw 0000000000408f40  = 1000.0  [PROOF]

So the enforced 35mm-equivalent range is **10 .. 1000 mm** inclusive. Note
the operand order: `maxsd %xmm1,%xmm0` with xmm0 preloaded 10.0 means the
*lower* bound wins on NaN-free input, and the min runs first, so the clamp
is order-safe.

SCOPE — the important subtlety [PROOF]
The clamp sits on the metadata/prior path only. The geometric estimate is
computed at 0xb6424f (`divsd`) and consumed directly; it never re-enters
0x7a17ea. Consequence: an EXIF focal is bounded to [10,1000] before use,
but a *derived* focal is bounded only below (4.0, section 3) and can in
principle exceed 1000. In practice a real lens cannot, so the asymmetry is
invisible — but a port must not assume the estimate is ceilinged.

Neighbouring value, for orientation (no focal xref): 0x321ac68 = 0.0025.

3. THE PLAUSIBILITY FLOOR 4.0 AND THE 50 px GATE
================================================================
The estimator does not clamp the estimate — it *substitutes* the default
when the estimate is implausible. Threshold 4.0 mm:

  slice 0x2da51a8  FAT 47,878,568  raw 0000000000001040  = 4.0     [PROOF]

  slice 0xb641b0  FAT 11,960,752  movsd -0x3cd8(%rbp),%xmm0   ; focal
  slice 0xb641b8  FAT 11,960,760  movsd 0x2da51a8(%rip),%xmm1  ; 4.0
  slice 0xb641c0  FAT 11,960,768  ucomisd %xmm0,%xmm1
  slice 0xb641c4  FAT 11,960,772  ja 0xb64279                 ; 4.0 > f
  slice 0xb6424f  FAT 11,960,911  movsd -0x3a30(%rbp),%xmm0   ; est (px)
  slice 0xb64257  FAT 11,960,919  divsd -0x3ef0(%rbp),%xmm0   ; / px per mm
  slice 0xb6425f  FAT 11,960,927  movsd %xmm0,-0x3cd8(%rbp)   ; store est
  slice 0xb64267  FAT 11,960,935  movsd 0x2da51a8(%rip),%xmm1
  slice 0xb6426f  FAT 11,960,943  ucomisd %xmm0,%xmm1
  slice 0xb64273  FAT 11,960,947  jbe 0xb641ca                ; 4.0 <= est
  slice 0xb64279  FAT 11,960,953  movabs $0x4041800000000000  ; else 35.0
  slice 0xb64283  FAT 11,960,963  movq %rax,-0x3cd8(%rbp)
  slice 0xb6428a  FAT 11,960,970  movb $0x1,%al
  slice 0xb6428c  FAT 11,960,972  movq %rax,-0x3f00(%rbp)    ; "used default"
                                                                flag = 1

Both comparisons are unsigned-ordered forms, so a NaN focal takes the
`jbe` / falls through and is **kept**, not replaced. The fallback sets a
sticky boolean at -0x3f00, i.e. the caller can tell a measured 35 from a
defaulted 35. [PROOF for the flag; INFERENCE for its downstream use]

Second, independent plausibility gate on *pixel* focal from metadata:

  slice 0x2da4698  FAT 47,875,736  raw 0000000000004940  = 50.0    [PROOF]
  slice 0xb63ef3  FAT 11,960,051  ucomisd %xmm1,%xmm0 ; jbe 0xb6430d
      -> if the metadata focal is < 50 px, -0x3cf0 is forced to 0.5 and the
         r12 flag is cleared (0xb63efd-0xb63f10). [PROOF]

So there are three escalating sanity rules. The first two *replace* the
value rather than clamp it (<50 px -> distrust the scale; <4.0 mm -> 35.0);
only the third is an actual clamp (outside [10,1000] -> clipped, section 2).

4. PIXEL -> 35mm CONVERSION = FIXED 36 x 24 mm (question 4)
================================================================
The long edge is a hard-coded 36.0 and the short edge a hard-coded 24.0.
They are consumed as a **diagonal** through hypot():

  slice 0x2da55f0  FAT 47,879,664  raw 0000000000003840  = 24.0    [PROOF]
  slice 0x321ac88  FAT 52,554,888  raw 0000000000004240  = 36.0    [PROOF]

  slice 0xb63ff4  FAT 11,960,308  movl %r15d,%eax ; cvtsi2sd -> xmm0 (h px)
  slice 0xb63fff  FAT 11,960,319  movl %r13d,%eax ; cvtsi2sd -> xmm1 (w px)
  slice 0xb6400a  FAT 11,960,330  callq 0x2c51174 <_hypot>
  slice 0xb6400f  FAT 11,960,335  movsd %xmm0,-0x3ef0(%rbp)  ; diag_px
  slice 0xb64017  FAT 11,960,343  movsd 0x2da55f0(%rip),%xmm0 ; 24.0
  slice 0xb6401f  FAT 11,960,351  movsd 0x321ac88(%rip),%xmm1 ; 36.0
  slice 0xb64027  FAT 11,960,359  callq 0x2c51174 <_hypot>   ; 43.266615 mm
  slice 0xb6402c  FAT 11,960,364  movsd -0x3ef0(%rbp),%xmm1
  slice 0xb64034  FAT 11,960,372  divsd %xmm0,%xmm1          ; px per mm
  slice 0xb64038  FAT 11,960,376  movsd %xmm1,-0x3ef0(%rbp)  ; SAVED scale
  slice 0xb64044  FAT 11,960,388  movsd -0x3cd8(%rbp),%xmm0  ; focal (mm)
  slice 0xb6404c  FAT 11,960,396  mulsd %xmm1,%xmm0          ; -> pixels
  slice 0xb64050  FAT 11,960,400  movsd %xmm0,-0x3888(%rbp)  ; param

hypot(36,24) = 43.266615305567875 — the full-frame diagonal. The image
diagonal in pixels divided by it gives pixels-per-mm on the assumption the
frame *is* 36x24. There is no sensor-size, crop-factor or EXIF-make lookup
in this conversion: any camera is treated as full-frame. [PROOF for the
constants and the arithmetic; INFERENCE that no sensor query exists, based
on the two constants being immediate rather than loaded.]

The same 24/36 pair recurs in a second function as a literal pair:
  slice 0x144a00 FAT 1,346,048  movsd 24.0
  slice 0x144a08 FAT 1,346,056  movsd 36.0
  slice 0x144a10 FAT 1,346,064  callq <_hypot>  ; *0.5 (0x2da2e10)
  slice 0x144a15 FAT 1,346,069  mulsd 0x2da2e10 = 0.5
  slice 0x144a49 FAT 1,346,121  movsd 4.0 ; callq <_pow>   ; f^4
  slice 0x144a7a FAT 1,346,170  movsd 6.0 ; callq <_pow>   ; f^6
i.e. the diagonal also feeds a radial (f^4/f^6) polynomial. [PROOF]

Useful negative: 36.0f/35.0f float32 forms exist (0x8e7720c / 0x8e77210,
a 35.0f,36.0f pair) but are **unreferenced** — the live constants are the
doubles above. [PROOF]

5. THE PRIOR WEIGHT (question 3) — there isn't one
================================================================
5.1 The estimator's control flow is winner-take-all [PROOF]
The focal source is selected by `UprightFocalMode` through a 4-entry jump
table at slice 0xb65670 (FAT 11,966,064):

  index 0 -> 0xb63e78  auto: metadata probe, else fall through
  index 1 -> 0xb63f29  force focal := 0.0 and bl := 0  (estimate path)
  index 2 -> 0xb63e88  read metadata directly
  index 3 -> 0xb63f15  bl := 1; keep stored focal only if >= 4.0,
                       else focal := 0 and bl := 0
  (dispatch: 0xb63e58 cmpq $0x3 ; 0xb63e76 jmpq *%rax)

Then, at the join:
  slice 0xb641a8  testb %bl,%bl
  slice 0xb641aa  je 0xb6424f        ; bl==0 -> GEOMETRIC ESTIMATE
  slice 0xb641c4  ja 0xb64279        ; bl==1 -> metadata wins, or 35.0

bl==1 (a metadata focal of at least 4.0 mm) short-circuits straight past
0xb6424f. So when EXIF supplies a usable focal the estimate is **never
computed**, and when it does not the estimate is used **raw**. There is no
`(1-w)*geom + w*prior` anywhere between 0xb641a8 and 0xb64302. [PROOF]

  PORTING IMPLICATION: a port should implement a discrete source
  selector with the 4.0 floor and the [10,1000] clamp on the prior branch,
  not a weighted prior residual. The "prior weight" is not tunable in this
  build and cannot be fitted from behaviour — it is a switch, so any
  attempt to fit a small w against the geometric residual will be fitting
  noise from the branch rather than a real coefficient.

(FAT 52,554,624..52,554,896). It contains 35.0 (0x321abb0), 1000.0

neighbourhood a focal weight *would* live in. Full dump of the block, for

5.3 What "heavily regularised" means here, concretely
Not a large weight: the estimator is regularised by *distrust thresholds*
(50 px, 4.0 mm) and by a fallback to the population mode (35 mm), and the
prior branch is hard-gated to [10,1000]. Behaviourally the prior dominates
completely whenever metadata exists, which is why the earlier corpus work
saw focal estimates pinning near 35 on metadata-poor files.

8. FALSE LEADS
================================================================
- The four "settings" xref clusters are NOT a clamp site; 0xa1157 and
  0x12cade are pure (de)serialisers and 0xb65c98/0xb66202 likewise. The
  clamp is only at 0x7a17ea, in a different function ~3.9 MB lower.
- 0x8eb58a8 is the wrong (FAT-relative) address for the focal string. The
  objdump comment addresses are slice-relative; searching a FAT-offset
  disassembly for them yields nothing. This cost a false start here and
  will bite anyone repeating it.
- 0x321abb0 has 40+ `movsd` xrefs across the binary; most are unrelated
  modules using 35 as a plain number. Only 0x7a16f1/0x7a170c are proven
  focal uses; 0x8fe8a3 divides by 35.0 and is only plausibly a 35 mm
  normalisation.
- 500.0 (0x2da5628) and 400.0 (0x85a7870) are NOT the focal ceiling. 500
  is a global magic across ~10 modules; 400.0 is loaded once into a solver
  param block (0xb63c30) beside 5e-05 (0x85a7860) and is almost certainly
  an iteration cap, not a bound.
- 10.0 also occurs as a float32 at 0x85a7850 used at 0xb61479, inside an
  unrelated sqrt/normalise kernel. Not the clamp.
- The Lua parameter schema (Resources/AgDevelopParams.lua) contains the
  key names but is compiled bytecode and declares no min/max for the focal
  — the range is not declarative, it is only in code.

9. SUMMARY OF THE FOUR ANSWERS
================================================================
1. fallback focal       35.0 (f64), four sites incl. the <4.0 failure path
2. enforced range       10.0 .. 1000.0, `max(10,min(f,1000))`, prior path
                        only; estimate floored at 4.0 but not ceilinged
3. prior vs residual    no weight — winner-take-all source switch on
                        UprightFocalMode; prior fully dominates when a
                        usable EXIF focal (>= 50 px, >= 4.0 mm) exists
4. pixel->35mm          fixed full-frame 36 x 24 mm via hypot(36,24) =
                        43.266615 mm diagonal; 36.0 confirmed, no sensor
                        lookup
