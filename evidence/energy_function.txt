1. CORRECTION TO THE PREMISE: HOW THE SIGMAS ARE ACTUALLY STORED
--------------------------------------------------------------------
Bit-exact search of the WHOLE file:

    float32  pi/12 = 0.2617993877991494 -> 920a863e  0 hits
    float32  pi/15 = 0.20943951023931953 -> 5077563e 0 hits
    float64  pi/12  (LE)                              0 hits
    float64  pi/15  (LE)                              0 hits

So the sigmas are NOT stored as exact pi/12, pi/15. They are stored as
ROUNDED DECIMAL LITERALS, and only inside test-fixture tables:

    130,461,984  float32  0.261799991  (bytes a60a863e)  <- 0.2618f, the ONLY occurrence
    275,584,536  float32  0.261799991  (bytes a60a863e)  <- arm64 twin of the above
    130,436,352  float32  0.209399998  (bytes f46c563e)  <- 0.2094f
    275,558,904  float32  0.209399998                    <- arm64 twin

0.2618f and 0.2094f are ~1.4e-6 / ~4.0e-5 from pi/12 and pi/15
respectively — i.e. a 4-decimal authored literal, NOT the true constant.
Earlier "sigma present as float32" was probably a tolerance match
(|v-0.2618| < ~5e-4 also catches the whole 0.261..0.262 neighbourhood).

IMPORTANT: 0.2618f and 0.2094f NEVER OCCUR ADJACENTLY. With a +-5e-4
window over both __const ranges, the only pair within 8 floats is
124,395,420 / 124,395,452 (and its twin 269,537,364 / 269,537,396).
No struct holds {sigma_v, sigma_h} together.

2. THE FIXTURE RECORD FORMAT (decoded — this is the main structural find)
--------------------------------------------------------------------
At 130,436,352 and 275,558,904 the records are a clean, unambiguous
24-byte stride. Layout (little-endian):

    +0  float   rotation / roll angle   (radians, e.g. -0.2102, 0.0030)
    +4  float   distortion-ish small coefficient (1e-4 .. 2e-4)
    +8  u32     0
    +12 u32     enum tag: 6, 8, or 9
    +16 i32     +1 / -1
    +20 u32     0

Sample records (offset, angle, coeff, tag):
    130,436,232  -0.2102  0.000125613  6
    130,461,936   0.0030  0.000192668  8
    130,461,960   0.1330  0.000207134  8
    130,461,984   0.2618  0.000216895  8   <-- sigma_v record
    130,436,352   0.2094  0.0001256...  6   <-- sigma_h record

The angle field = sigma when the tag selects that mode. So sigma_v/sigma_h
here are per-case INPUTS to a solver, not the shipped default weights.

These records ARE code-referenced (x86_64, `lea rsi,[rdi+rax]` table walks
at 0x106E51C and 0x1071648), inside a vectorised 24-byte-stride kernel at
0x106E320. The kernel's only float constant is at 0x545FB00, which is a
BYTE MASK 0x02020202..., not a float (0x02020202 read as float =
9.551468e-38). So it is a pmulld/permute helper, not the energy evaluator.

3. THE OTHER BIG FIND: A 4,892-ENTRY MONOTONIC SIGMA SWEEP
--------------------------------------------------------------------
275,598,848 .. 275,637,984, 8-byte records {u32 tag=1, float value},
strictly non-decreasing, range 0.015718013 .. 0.49999145, min step ~2e-6.

    first 5 values: 0.015718013, 0.015722292, 0.016284492, 0.016849043, 0.017314635
    last  5 values: 0.499995708, 0.499991447, 0.499987155, 0.499982893, 0.499936283
    nearest entry to pi/15 = 0.209411860 (idx 1468, delta -2.8e-5)
    nearest entry to pi/12 = 0.261752635 (idx 2082, delta -4.7e-5)

pi/12 and pi/15 are NOT special entries in the grid (uniform ~1e-5
spacing, no snap). So this is a generic lookup table used to map a
continuous sigma onto a discretised sweep — consistent with a sigma sweep
being run for every image, which corroborates sigma_v/sigma_h as real
tunables, but the table itself gives no exact constant.

4. WHAT THE .RODATA ACTUALLY IS (why constants are so hard)
--------------------------------------------------------------------
The whole __const range is dominated by generated test fixtures, not by
hand-written parameter blocks. Measured "6-decimal-exact" fraction
(authored fixture literals):

    130,436,000 (sigma_h fixture table)  0.251
    275,584,400 (sigma_v fixture table)  0.227
     69,892,400                          0.021   <-- NOT fixtures
    124,395,000                          0.018   <-- NOT fixtures

Baseline plausibility ((|v| in 1e-5..1e5)) is a flat ~0.13-0.14 across
essentially every 4 MB window of __const, so density heuristics do not
separate parameters from data. Big referenced float blocks like
0x1172A700 and 0x1172B700 are random N(0,0.4) MATRICES (test tensors).

The two non-fixture bands (69.7M-70.1M and 124.0M-124.5M) hold the only
"real" hand-written .rodata scalars. Ranked candidates from those bands
below (§5, tier B). They are, however, mostly UNREFERENCED by x86_64 code
(0-1 refs within 400 bytes) and their arm64 twins are unreferenced too,
so they are cold data — likely a serialised parameter/calibration blob
rather than live immediates.

6. WHERE THE PAPER'S NAMED TERMS WOULD BE, AND WHAT'S MISSING
--------------------------------------------------------------------
Mapped onto the paper, the expected constant block would be:
 eye-line weight, picture-frame weight, image-Jacobian weight,
 focal-prior weight, Perkins-junction barrier, and the two exponents.
No block of 6+ weights with unit-ish magnitudes exists adjacent to either
sigma literal. The closest structural analogue is the fixture record
{angle, coefficient, tag, sign}, which carries only ONE scalar besides the
angle — suggesting the shipped code parameterises a case by (angle, one
coefficient, mode) and that the per-term weights are COMPILED IN as
immediates rather than tabulated.

That last point matters: 42,265 plausible float immediates live inline in
x86_64 __text (mostly libm polynomial tables, e.g. -274.5625, 13.6875),
and 0.2618/0.2094 appear nowhere as text immediates either. If the weights
are immediates they are only reachable by disassembling the caller of the
energy evaluator, which has no symbol.

3. Re-run the behavioural sweeps (existing sweep_fit.json) against
   sigma_v/sigma_h around 0.2618/0.2094 rather than pi/12, pi/15, since
   the binary demonstrably encodes the 4-decimal forms.
4. Treat any weight in tier B as a hypothesis to fit, not a fact.
